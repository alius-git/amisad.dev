==== Design - Part 1

Act as the Principal Systems Architect for AmisAd. Based on the planning files
(plan/applications.md, plan/personas.md, plan/scenarios.md), create the design for a
proof-of-concept (POC) set of applications that can later grow into the full
cloud-hosted and mobile ecosystem.

POC environment: everything runs in local virtual machines, plus test mobile devices
side-loading the POC mobile app. VM provisioning, deployment, and end-to-end
verification are driven by the Yuruna framework, executing the sequences in
plan/scenarios.md against synthetic data.

Deliverables: a master plan/design.md, plus Mermaid diagrams under plan/design/ —
one overall POC architecture diagram and one per application (for the format, see
https://github.com/alissonsol/yuruna/tree/main/docs/design). Before writing, ask
only the design questions the principles below do not already settle.

Design principles:
- Server-side applications run in K8s clusters and stay cloud-agnostic: no managed
  cloud services; every dependency must run in-cluster.
- PostgreSQL is the only database. Implement the ledgers (consent, settlement,
  attestation) as append-only, hash-chained tables — no blockchain.
- Telco-local "slice VMs" stay light and stateless: matches run in ephemeral,
  confidential-computing environments. Where POC hardware lacks TEE support,
  simulate attestation behind the same interface, so production hardware is a
  drop-in replacement.
- Simulate what the lab lacks (SIM-anchored identity, carrier slice control,
  payments) but preserve production contracts: every mock implements the real
  interface, and swapping it must not change any caller.
- POC scope is scenario-driven: include exactly the applications and foundations
  needed to execute SCENARIO-001 through SCENARIO-010 end to end; stub nothing a
  scenario asserts against.
- AmisAd/buyer is a mobile, offline-first app (side-loaded); all other user-facing
  applications are web apps served from the cluster.
- Minimize the technology count: one primary backend language/framework (propose
  it), versioned OpenAPI-documented REST between applications, and one lightweight
  in-cluster message broker for the event-driven flows.
- Authentication is OIDC-style tokens from a mock identity service standing in for
  Identity & Verification; secrets live in cluster secret storage.
- Non-goals for the POC: performance and scale, real payments, real creative
  production, and production security hardening beyond what the scenarios verify.

==== Code skeletons

Act as the Principal Systems Architect for AmisAd. Based on the amisad.com content
(brand assets) and the amisad.dev plan/ documents (applications, scenarios, design),
create the POC code skeletons under poc/, mirroring the yuruna-project layout so the
Yuruna runner can discover and drive them.

Layout (yuruna-project convention; update design.md §6 to match, and note the change
in README.md if it describes the layout):
  poc/
    MODULE.bazel  .bazelversion  BUILD.bazel   # Bazel root, bzlmod, pinned via bazelisk
    build/                                      # doctor + helper scripts (PowerShell)
    contracts/                                  # OpenAPI + event schemas (kept from design)
    components/
      services/<name>/                          # 10 Rust services: seller-svc, resource-svc,
                                                #  ads-svc, insights-svc, platform-svc, audit-svc,
                                                #  connect-svc, fabric-coordinator, identity-mock,
                                                #  ledger-svc
      edge/slice-runtime/                       # Rust slice runtime
      apps/buyer-flutter/                       # Flutter placeholder app
      apps/web-spa/                             # React+TS+Vite shell, 6 role-module routes
      art/                                      # brand assets copied from amisad.com:
                                                #  icon.svg, icon-64.png, palette tokens
                                                #  (#2B3A67 navy, #E2725B terracotta), README
    config/localhost/{resources,components,workloads}.yml   # three-phase deploy skeletons
    workloads/<group>/<name>/                   # minimal Helm chart per service
    db/                                         # schema.sql + seed skeletons per scenario
    test/
      gui/                                      # 10 sequence YAMLs, seq per SCENARIO-001..010,
                                                #  plus one k3s+PostgreSQL+NATS baseline sequence
      ubuntu.server.24/                         # guest scripts the sequences fetch-and-execute

Build rules:
- Bazel is the single entry point: `bazel build //...` must succeed on the first try
  on a machine with bazelisk, rustup, Node, and the Flutter SDK installed (all three
  toolchains are REQUIRED — build/doctor.ps1 checks versions and fails fast with a
  clear message before any build starts).
- Rust: rules_rust with a pinned toolchain and crate_universe lockfile; one library +
  binary target per service; a shared crate for common config/health plumbing.
- Flutter and web-spa: Bazel targets that wrap the flutter/Vite CLIs (genrule or
  sh_binary) — Bazel orchestrates, the native toolchains do the work.
- Container images are built by a script target (build/images.ps1), not part of the
  `bazel build //...` gate — Docker may be absent on dev machines.

Skeleton depth — deployable, not just compilable:
- Each Rust service: GET /health and GET /version, config from environment variables,
  multi-stage Dockerfile, and a minimal Helm chart under workloads/ that deploys it
  with a liveness probe on /health.
- buyer-flutter and web-spa: placeholder screens using the art/ brand assets; the SPA
  shell routes to six empty role modules (seller, resource, ads, insights, platform,
  audit, connect share the shell per design).
- contracts/: one OpenAPI stub per service declaring only /health and /version now.

Test skeletons:
- Each test/gui/ sequence must validate against yuruna/test/schemas/sequence.schema.yml:
  unique sequenceGuid, sequenceRevision 1, description naming its SCENARIO, baseline
  chain to the k3s+PostgreSQL+NATS baseline sequence, and steps that fetch-and-execute
  guest scripts which currently deploy the skeletons, curl /health, and end with a
  TODO block enumerating the scenario's real steps from plan/scenarios.md.
- Guest scripts: bash, set -euo pipefail, one per sequence plus shared bring-up,
  modeled on the yuruna-project text-to-sql example.

Done when: build/doctor.ps1 passes; `bazel build //...` is green; every Helm chart
passes `helm lint`; every sequence YAML validates against the schema; design.md §6
reflects this layout; nothing references paths that do not exist.
